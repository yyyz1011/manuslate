# PatchMark 北极星产品蓝图

更新日期：2026-09-11

## 1. 产品野心

PatchMark 要成为 AI 时代最强的 Markdown 软件，但“最强”不等于功能数量最多。

可验证的定义是：

> 它既达到专业 Markdown 编辑器的完成度，又能让一个不了解旧目录的人快速接管、理解、分类、治理和发布大量 Markdown；AI 的每个结论有来源，每个动作可审阅，每次批量变更可回滚。

### 北极星指标

新用户打开一个包含 1,000 个 Markdown 文件的陌生目录后：

1. 60 秒内看懂资料规模、主要类型和高风险问题。
2. 10 分钟内建立第一版可用分类体系。
3. 15 分钟内安全完成一组批量治理并成功回滚一次。
4. 一周后新增文件只需要处理“增量待办”，不重新整理全库。

## 2. 七个核心引擎

### 2.1 Markdown Engine：专业编辑底座

目标：单独拿掉 AI，仍然是一款值得长期使用的 Markdown 编辑器。

- CommonMark/GFM 严格模式与可选方言配置
- 源码、Live Preview、编辑＋预览、纯阅读
- 表格可视化编辑、列表智能缩进、任务、脚注、公式、Mermaid、警告块
- YAML/TOML/JSON Frontmatter 读取，YAML 表单双视图
- 大纲、文档地图、折叠、多光标、正则替换、片段、命令面板
- 图片粘贴、拖放、重命名、压缩建议、alt/caption 和相对路径
- 拼写、术语、风格、markdownlint/textlint 类规则
- 超大文件降级、中文输入法、RTL、无障碍和主题
- HTML/PDF；通过 Pandoc 扩展 DOCX、EPUB、LaTeX 等格式

与 Typora 的差异不是更花哨，而是同时保留源码可信、diff、外部文件协作和资料库治理。

### 2.2 Catalog Engine：资料目录与虚拟视图

目标：不移动文件，也能获得数据库式管理体验。

- 文件树、表格、卡片、列表、看板和时间线
- 任意 Frontmatter 字段作为列、筛选、分组和排序条件
- 文件属性、链接属性、计算字段和聚合
- 智能集合保存在本地索引或显式 `.patchmark/views/` 文件
- 自然语言筛选必须转换成用户可见、可编辑的规则
- 同一文件可进入多个集合，不复制正文
- 保存视图支持“未分类”“待复查”“发布候选”“半年未更新”等日常队列

Obsidian Bases 已把多视图抬高为基线。PatchMark 的新增价值是让 AI 自动从旧资料中提出视图、字段和分类规则，并能评估其覆盖率和冲突。

### 2.3 Governance Engine：资料库治理

目标：把“维护文档”从零散脚本变成可重复的管理流程。

- 内容清单、格式分布、字段覆盖率和变化趋势
- 坏链、死链、孤立、歧义、循环引用和标题锚点漂移
- 精确重复、近似重复、版本分叉和可能可合并内容
- Frontmatter schema、字段别名、类型冲突和枚举漂移
- 标签同义词、孤立标签、过度标签和层级混乱
- 图片/附件缺失、重复、未引用、绝对路径和体积异常
- 过期迹象、矛盾、缺少负责人/状态/更新时间
- 发布路由、slug、导航、摘要、SEO 和多语言缺口

所有问题必须区分：确定性错误、需要人工判断、AI 推断、信息提示。不能把它们混成一个虚假的“82 分健康度”。

### 2.4 Transaction Engine：安全批量变更

目标：这是 PatchMark 相对脚本和普通 CMS 最重要的信任壁垒。

```mermaid
flowchart LR
    S[选择范围] --> P[生成计划]
    P --> I[影响分析]
    I --> R[分组审阅]
    R --> A[原子应用]
    A --> V[重新索引与验证]
    V --> O[审计记录]
    O --> B[一键回滚]
```

- 每个计划固定文件路径和基准 hash
- 支持字段 patch、文本 patch、重命名、移动、归档和引用更新
- 应用前显示精确 diff、受影响链接、冲突和预计模型费用
- 尽量以一个资料库事务执行；无法原子化时保留完整补偿操作
- 部分失败明确区分成功、失败、跳过、冲突和未执行
- 执行后自动运行目标检查，不以“写入成功”代替结果正确
- 回滚同样先显示计划，防止覆盖后来产生的新修改

### 2.5 AI Steward Engine：AI 资料管理员

目标：AI 不只是聊天或润色，而是长期维护资料秩序。

#### 接管

- 对旧目录生成内容地图、主题簇、文档类型和异常清单
- 识别现有目录、标签和字段背后的隐含规则
- 提出分类树、字段 schema、生命周期和命名规范
- 对每个建议给出代表文件、反例和无法判断的边界

#### 日常分流

- 新文件进入 Inbox，AI 建议类型、主题、项目、状态和目标集合
- 高置信度也只进入待确认队列；规则可以由用户选择升级为自动虚拟分类
- 记住用户纠正，形成可查看的正例、反例和优先级规则

#### 治理

- 同义标签归并、错放主题、近似重复、矛盾和过期迹象
- 生成合并提纲、归档理由、缺口报告和治理优先级
- 每个结论引用文件、标题/行号、hash 和索引时间

#### 辅助写作

- 局部改写、总结、翻译、术语统一和结构审查
- 入口弱于管理功能，所有修改仍进入 Patch 审阅

### 2.6 Context Engine：可检查的 AI 上下文

目标：解决“喂得太少答不准，喂得太多贵且泄露”的问题。

- 从集合、搜索、链接深度、目录或人工勾选构建上下文包
- 每个片段显示纳入原因、来源、hash 和 token
- 去重、敏感目录排除、代码块/附件策略和预算上限
- 支持全文搜索、可选 embedding 和 rerank；结果解释不能只给相似分
- 保存 Context Recipe，供重复任务、外部 AI 或 Agent 使用
- 输出带来源 Markdown、JSONL 或通过模型适配器直接调用

### 2.7 Publish & Agent Engine：发布和开放接口

目标：让 Markdown 从资料库可靠流向人和 AI。

- GitHub、VitePress、MkDocs、Hugo、Hexo、Quartz 等配置档
- 目标方言渲染、路由、导航、静态资源和构建错误检查
- 发布前变更集、目标预览和检查报告
- CLI 查询、批量检查和 CI 退出码
- MCP 提供搜索、读取、集合、健康报告和上下文包
- Agent 默认只读；写操作只能创建待审批 Governance Plan
- 插件使用声明式权限：文件范围、网络、密钥、命令和写入能力

## 3. 六个关键体验时刻

### 3.1 第一次打开：不是空白编辑器

显示扫描进度和确定性结果；AI 分析是明确的第二步。用户先看到：

- 发现 1,286 个 Markdown、214 个附件
- 4 种 Frontmatter 结构、19 个疑似同义标签
- 31 个坏链、8 组精确重复、47 个未分类文件
- 其中 22 个目录被排除，不会发送给 AI

### 3.2 AI 提出分类体系：不是直接打标签

界面同时展示类别树、代表文档、边界说明、覆盖率、冲突率和未判断数量。用户修改一个类别后，只重新评估受影响文件。

### 3.3 每日 Inbox：只处理变化

新增、外部修改、AI 低置信度、规则失败和待复查内容进入统一收件箱。处理完成后归零，而不是每次重扫全库制造新噪声。

### 3.4 批量治理：先看影响，再按按钮

用户选择“合并 `dev` 与 `development` 标签”时，先看到 38 个字段 patch、3 个保存视图变化和 2 个异常 YAML 文件；异常文件不会被强行改写。

### 3.5 阅读一个文档：看见上下文和血缘

右侧同时显示大纲、反向链接、相关文档、当前问题、最近变更，以及哪些内容来自 AI 建议但尚未人工确认。

### 3.6 发布：看到目标世界

选择 GitHub 或 VitePress 后，预览采用对应方言和路径规则；检查结果直接关联到可审阅修复，而不是只吐出构建日志。

## 4. AI 可信设计

### 4.1 每项 AI 结论的数据契约

```ts
type AIInsight = {
  id: string
  kind: 'classification' | 'duplicate' | 'contradiction' | 'staleness' | 'gap'
  statement: string
  evidence: Array<{
    path: string
    contentHash: string
    lineStart?: number
    lineEnd?: number
    excerpt: string
  }>
  confidence: number
  uncertaintyReason?: string
  provider: string
  model: string
  createdAt: string
  reviewStatus: 'unreviewed' | 'accepted' | 'rejected' | 'needs_context'
}
```

置信度只用于排序，不作为真实性证明。没有 evidence 的结论不得进入批量治理计划。

### 4.2 分类质量评估

- 用户可把已确认文件保存为小型 Golden Set
- 新模型、新提示词或分类树先在 Golden Set 上比较
- 展示覆盖率、冲突数、低置信度数和人工修正率
- 模型升级不会静默重分类全库
- 每次大规模重分类都创建新的 taxonomy version，可比较和回退

### 4.3 多模型与成本控制

- 快速模型做摘要和初筛，强模型只处理边界案例
- embedding 是可选能力，不作为编辑器运行前提
- 按 content hash 缓存，未变化文件不重复付费
- 任务开始前显示文件数、文本量、模型和估算费用
- 提供硬预算、并发、速率、暂停、续跑和错误重试

## 5. 信息架构

```text
工作区
├── 总览          规模、变化、风险、分类覆盖
├── Inbox         新文件、低置信度、冲突、待复查
├── 资料          文件树、表格、卡片、看板、智能集合
├── 文档          编辑、阅读、上下文、血缘、Diff
├── 分类          taxonomy、schema、样本、版本和评估
├── 治理          问题队列、变更计划、验证和回滚
├── 上下文        搜索、语义发现、Context Recipe
├── 发布          目标配置、预览、构建和检查
└── 设置          方言、规则、模型、隐私、插件、Agent
```

默认只展示“总览、Inbox、资料、文档、治理”五个入口；高级入口随功能启用，避免强大等于杂乱。

## 6. 分阶段路线

### Phase 0：可信文件核心

- 打开/保存零改写、文件监听、快照、diff、三方合并
- Markdown 解析、索引和 10,000 文件性能基准
- 安全渲染、中文输入法和崩溃恢复

完成门槛：未建立可信文件核心前，不接入能写文件的 AI。

### Phase 1：Takeover

- 总览、资料表、组合搜索和增量 Inbox
- Frontmatter/schema、链接、资源、重复和命名检查
- 专业源码编辑、预览、大纲和表格辅助

完成门槛：陌生用户能在 60 秒内理解测试资料库，并且扫描零改写。

### Phase 2：Organizer

- AI 分类体系建议、虚拟集合、低置信度人工队列
- 分类规则、正反例、Golden Set 和 taxonomy version
- BYOK/BYOM、多协议适配、本地模型和费用控制

完成门槛：分类建议对 Golden Set 可量化，模型变化不会静默改库。

### Phase 3：Governor

- 多文件 Governance Plan、影响分析、执行、复查和回滚
- 标签/schema 迁移、重命名、移动、归档、链接更新
- 内容血缘和完整审计

完成门槛：真实资料库成功完成并回滚一次复杂治理事务。

### Phase 4：Context & Publish

- 语义检索、上下文包、发布配置档、构建诊断
- Git/CI、CLI 和只读 MCP

完成门槛：同一集合能可靠服务编辑、AI 上下文和发布检查。

### Phase 5：Platform

- 权限化插件、写计划 MCP、可审查自动化
- 可选团队协作和可选官方托管模型服务

完成门槛：任何第三方扩展都不能绕过文件权限、计划审阅和审计。

## 7. 竞争胜法

| 对手 | 不正面复制 | PatchMark 必须赢在哪里 |
|---|---|---|
| Typora / MarkText | 单篇所见即所得细节 | 强编辑不输，同时有源码可信、全库管理和安全 AI |
| Obsidian | 插件数量、Canvas 生态 | 零配置接管、schema 推导、批量治理事务和 AI 审计 |
| Front Matter CMS | 静态站点框架专用配置 | 任意 Markdown 库、AI 分类体系、内容质量和回滚闭环 |
| Logseq / SiYuan / Trilium | 块数据库和专有知识模型 | 原文件保真、外部工具共存、无迁移锁定 |
| Khoj / AnythingLLM | 通用聊天与 Agent 数量 | AI 结果能沉淀成资料规则、问题、计划和验证结果 |
| Zettlr / MWeb | 学术引用或平台发布广度 | 资料治理主流程、目标方言检查和开放适配器 |
| VS Code＋脚本 | 无限可编程性 | 非开发者可理解、影响可见、事务可回滚、结果可验证 |

## 8. 明确不做

- 不把聊天框放在首页中心。
- 不把图谱当默认入口。
- 不为了数据库视图把 Markdown 转成私有块格式。
- 不把基础管理能力拆散到必须安装的插件中。
- 不允许 AI 根据单次回答直接批量覆盖文件。
- 不声称一个模型评分等于资料质量事实。
- 不在首版做多人实时协作、白板、移动端或插件市场。
- 不用“功能最多”掩盖盘点、分类、治理、验证主流程没有跑通。

## 9. 开源护城河

代码开源不意味着没有壁垒。护城河来自：

- 大量真实 Markdown 方言、Frontmatter 和路径兼容测试集
- 多文件变更、冲突和回滚的稳定性
- 可解释分类与资料治理的交互范式
- 社区共享的规则包、schema 模板和发布配置档
- 本地优先、模型中立和不锁定文件形成的长期信任

项目应鼓励贡献兼容规则、检查器、发布配置和模型适配器，而不是一开始开放能任意读写文件的无边界插件 API。
